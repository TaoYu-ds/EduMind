# 教育培训场景改造说明

> 这份文档记录 TutorMesh 从"电商客服"改造成"教育培训辅导"的全过程：改了哪些文件、为什么这样拆、有哪些取舍、以及几个关键设计追问的回答。
> 代码以 `TutorMesh/`（Python 版）为准；`TutorMeshFrontend/` 的示例文案已同步；Java 版（`TutorMeshJava/`，未包含在本仓库内）仍保留电商版本作为对照。

## 1. 一句话结论

把原来"通用 / 技术 / 账单 / 升级"四个客服角色，换成"学习服务台 / 讲题 / 计划 / 考试 / 升级"五个角色；把原来"订单、物流、退款、发票"的意图，换成"知识点提问、作业辅导、学习计划、考试信息、课程推荐"；把原来"能答就答"的知识库，换成"按学科章节难度结构化、先过滤再检索"的教材库。

改造后 **166 个测试全部通过**，核心链路（意图 → 路由 → 工具 → 记忆 → 评测）保持不变。

## 2. 为什么要换场景（不是换个皮）

原项目的架构能力（三路意图融合、主辅路由、RAG 工具、三级记忆、监控降级、LLM-as-Judge）是通用的，但"客服"场景里很多约束体现不出来：

| 原来的客服能力 | 教育场景里的对应问题 | 改造后怎么体现 |
| --- | --- | --- |
| 错误码排查 | 学生说"这个不会"，信息量几乎为零 | 查询改写 + 章节过滤 + 卡点归类 |
| 退款流程 | 作业辅导不能直接给答案 | 讲解脚手架 + 教学规范 Skill + 升级条件 |
| 账单核验 | 学习计划要能在真实作息里执行 | 计划编排 + 负荷校验两个确定性工具 |
| 发票/支付合规 | 考试时间、分数线不能编造 | 流程查询工具只给官方入口，不给数字 |
| 订单号槽位 | 学科/章节/年级要跨轮继承 | 三类槽位生命周期（身份/学科局部/任务局部） |

换句话说，改造不是换文案，而是换了一组**有明确正确性边界**的任务，这样 Agent 的"不编造""不越权""要可执行"才有地方落地。

## 4. 三个 Agent 为什么这样拆

### 4.1 TutorAgent：讲题的核心不是"知道答案"，是"定位卡点"

同一个"我不会"，可能是五种完全不同的原因：

- 概念不清：不知道定义和适用条件；
- 计算失误：思路对，符号/单位错；
- 审题偏差：漏看条件；
- 步骤遗漏：卡在第三步；
- 迁移困难：原题会，变式不会。

这五类对应五种干预方式。所以 Tutor 的流程被固定为：**归类卡点 → 检索教材 → 分层讲解 → 留自测题**。`classify_learning_blocker` 用确定性规则做归类，`build_explanation_scaffold` 按"概念/计算/证明/应用"给不同脚手架，避免模型每次自由发挥。

教学边界写进了三处，形成三层约束：

1. `AgentProfile.handoff_conditions`：要求代写整份作业 → 升级；
2. `system_prompt`：不直接给出可抄写的完整答案；
3. `skills/tutor_guidance/SKILL.md`：细化到"可以讲思路、拆步骤、给同类例题，不能输出整份答案"。

### 4.2 PlanAgent：计划的价值是"明天早上知道做什么"

`build_study_plan` 是纯确定性算法，不调用 LLM：

- 总时长 = 天数 × 每日分钟；
- 按 60% 补薄弱 / 25% 复盘 / 15% 练习切分；
- 薄弱学科权重 1.6，按权重分配学科预算；
- 按 40% / 35% / 25% 切三个阶段，每阶段给每日任务和检查点。

`check_plan_feasibility` 再判断负荷：所需时间 = 每科 180 分钟/周 + 每个薄弱章节 60 分钟/周；可用时间低于所需 60% 判"过载"，高于 150% 判"充裕"。

为什么要两个工具而不是让 LLM 直接写计划？因为 LLM 排的计划经常"看起来合理但算不出来"——总时长对不上、阶段没有检查点、一周七天排满没有缓冲。把算术交给代码，LLM 只负责表达和追问，是这类任务的稳定做法。

### 4.3 ExamAgent：合规优先于有用

考试场景最容易出的问题是"编造"：报名日期、缴费金额、分数线、录取结果，每年变化且分省不同。所以 ExamAgent 的设计原则是**宁可少说，不能说错**：

- 温度设为 `0.0`；
- `lookup_exam_process` 只返回流程步骤和官方入口，`verified=false`，明确写"以官方公告为准"；
- `check_exam_fields` 检查"考试名称 / 环节 / 省份"是否齐全，缺省份时先讲通用流程再追问；
- Skill 里写明拒绝"内部名额""付费提前查分"，并提示这是常见诈骗话术。

这类"能力边界"设计比"接入了多少个工具"更能体现工程判断。

## 5. 意图识别：粗细分组的真正用途

新增五个意图后，最容易踩的坑是"同一句话被拆到两个意图互相稀释"。例如：

- "什么是函数的单调性" → `knowledge_query`
- "这题不会做" → `homework_help`
- 两句都属于"知识类"诉求，但字面差异大，Embedding 容易各投一票。

所以保留原来的"粗意图分组 + Pattern 细化"：

```text
knowledge_query / homework_help / course_recommend  →  query 组
study_plan                                          →  request 组
human_handoff                                       →  escalation 组
```

投票时先累计组分数选组，再选组内具体意图；如果组内胜出的是粗意图 `query`，而 Pattern 给出同组细意图且分数 ≥ 0.5、组分数 < 0.8，就用细意图覆盖。

效果：学生说"这个不会"时，即使 LLM 只给出宽泛的 `query`，Pattern 命中"这题/不会做"也能纠正为 `homework_help`，从而路由到 Tutor 而不是学习服务台。这条规则在测试 `test_pattern_can_still_refine_within_the_winning_group` 里有覆盖。

## 6. 知识库结构化：从"能搜到"到"搜得准"

### 6.1 数据结构

每篇文档可以带六个过滤字段：

```json
{
  "title": "函数单调性的定义与判定",
  "subject": "数学",
  "chapter": "函数",
  "difficulty": "基础",
  "grade": "高一",
  "doc_type": "知识点",
  "content": "..."
}
```

这些字段会写进**每个切片片段**的 metadata（不是只写在文档级），因为 Chroma 的 `where` 过滤作用在片段上。

### 6.2 检索链路

`search_course_knowledge` → `course_knowledge_search` → `search_with_rewrite`：

1. LLM 把问题改写成 3 个子查询；
2. 每个子查询带上 `subject/chapter/difficulty` 过滤条件并行召回；
3. 合并去重；
4. LLM 重排取 Top-K；
5. 过滤为空时逐级放宽：去章节 → 去难度。

### 6.3 为什么改写要带过滤条件

学生说"这个不会"时，改写模型只能根据上下文猜学科章节。如果过滤条件参与改写，模型可能把"数学-导数"改成"物理-力学"，越改越偏。所以 `extra_params` **只作为召回约束，不进入改写 prompt**：改写负责"换问法"，过滤负责"圈范围"，两件事分开。

## 7. 学习画像：让"个性化"有依据

画像固定六个字段，原因是不固定字段就没法在代码里用：

| 字段 | 谁用 | 怎么用 |
| --- | --- | --- |
| `grade` | Tutor / Plan | 决定讲解深度、题目难度、计划基准 |
| `subjects` | Plan | 分配学科预算 |
| `weak_chapters` | Tutor / Plan | 讲题优先补弱项，计划加权 |
| `learning_goal` | Plan / Exam | 时间锚点（高考/考研/期末） |
| `study_time` | Plan | 容量约束 |
| `preferences` | Tutor | 表达方式（先例题还是先定义） |

更新走双通道：

- LLM 从最近 10 条消息提炼，能读懂"函数这块一做题就废"；
- 规则抽取年级/学科/章节/目标/时长，LLM 超时也能保住关键字段。

合并策略：列表取并集，标量用非空新值覆盖。这样"这轮没提年级"不会把年级清空。

`weak_chapters` 的规则抽取有邻近约束：章节词和"不会/薄弱/跟不上"必须在同一句的邻近位置，避免"我问过导数"被记成"导数薄弱"。

渲染时用中文标签（`年级：高二`）而不是直接塞 JSON，减少 prompt 噪音，也更利于模型引用。

## 8. 槽位生命周期：三类字段，三种规则

`merge_state()` 的核心不是"记住更多"，而是"该忘的忘掉"：

| 类型 | 字段 | 规则 | 反例（如果不这样） |
| --- | --- | --- | --- |
| 学生身份 | `grade`、`subject`、`exam_name` | 跨任务保留 | 每轮都问"你几年级" |
| 学科局部 | `chapter`、`difficulty` | 换学科清空 | 问物理时把"导数"当薄弱章节带过去 |
| 任务局部 | `duration`、`study_time`、`date` | 同任务域继承 | 上一轮的"30 天"污染这一轮 |

这条规则直接来自教育场景的真实对话：学生会在数学和物理之间来回切，但年级和目标不会变。

## 9. 评测：把"教学正确性"写进评分标准

Judge 提示词新增了三条教育场景规则：

- 只给结论不给推导依据、跳过学生卡住的步骤 → 降低完整性和有用性；
- 直接给出可抄写的完整答案 → 按违反教学边界处理，不能给高分；
- 给出未经核验的报名日期、分数线 → 视为不准确。

校准样例也换成教育内容，其中"违规代写作业"那条的 accuracy/completeness/helpfulness 全为 0，用来告诉 Judge：**相关不等于正确**。

内置意图用例覆盖五类教学意图 + 平台咨询 + 投诉/转人工；对话用例覆盖讲题、拒答代写、排计划、考试咨询和多轮追问。

## 10. 改造中做的取舍

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 是否保留旧电商意图 | 删除 | 留着会进入 LLM 的可选意图列表，模型可能返回 `refund`，污染教育场景 |
| 是否保留 TechnicalAgent | 删除，平台问题交给 General | 平台使用问题（回放、作业提交）不需要独立角色，会造成路由碎片化 |
| 考试数据是否入知识库 | 入，但只放流程，不放具体日期 | 日期每年变化、分省不同，写死就是埋雷 |
| 是否让 LLM 直接排计划 | 不，改为确定性工具 | 算术和时间分配交给代码更可靠 |
| 是否重建 Chroma collection | 是，改用 `course_knowledge` | 避免旧客服语料混入教材检索 |
| Java 版是否同步 | 否 | 主实现是 Python；Java 版标注为电商场景，避免半成品 |

## 11. 设计追问与回答（三个层次）

### 11.1 一句话讲清这次改造

> 我把一个多 Agent 客服项目改造成了在线教育辅导系统。核心不是换文案，而是换了三个有明确正确性边界的角色：讲题老师不代写作业、计划老师不承诺提分、考试顾问不编造日期。为了让"这个不会"这种模糊提问能检索到教材，我把知识库按学科章节难度做了结构化，检索时先过滤再向量召回，并保留查询改写；学生画像固定成年级、学科、薄弱章节等六个字段，讲题和排计划都直接用它。

### 11.2 追问"为什么这么拆 Agent"

> 因为三个角色的失败模式不同。讲题的失败是"讲错/代写"，所以要卡教学边界和教材依据；计划的失败是"排得不可执行"，所以要把算术交给确定性工具；考试的失败是"编造日期"，所以要把温度降到 0 并且只给官方入口。如果把三者塞进一个 prompt，约束会互相冲突，而且没法分别评测。

### 11.3 追问"知识库为什么不用纯向量"

> 教育知识是树状结构：学科 → 章节 → 知识点 → 难度。纯向量检索会串科，问"函数单调性"可能召回"数列单调性"甚至物理图像。加了 metadata 过滤后，可以先圈定学科章节再算相似度；过滤过严时逐级放宽，保证不会直接返回空。另外学生的原始提问常常是"这个不会"，所以改写是必需的，但过滤条件不能参与改写，否则会把学科改跑偏。

## 12. 怎么跑起来

```bash
# 1. 起依赖（Redis + ChromaDB + API）
docker compose up -d --build

# 2. 看角色和 Skills
curl -s http://localhost:8000/health | python -m json.tool
curl -s http://localhost:8000/skills | python -m json.tool

# 3. 结构化导入一篇教材（带学科章节）
curl -s -X POST http://localhost:8000/knowledge/add \
  -H "Content-Type: application/json" \
  -d '{"documents":[{"title":"数列单调性","subject":"数学","chapter":"数列","difficulty":"进阶","doc_type":"知识点","content":"数列单调性指 a_{n+1} 与 a_n 的大小关系……"}]}'

# 4. 验证过滤检索
curl -s "http://localhost:8000/search?query=%E5%8D%95%E8%B0%83%E6%80%A7&top_k=3" | python -m json.tool

# 5. 跑内置评测
curl -s -X POST http://localhost:8000/eval/run -H "Content-Type: application/json" -d '{}'
```

本地跑测试：

```bash
pip install -r requirements-dev.txt
pytest -q          # 期望 166 passed
```

## 13. 还没做的部分

- 题库/作业系统对接：现在只能靠学生贴题目，无法按题目 ID 拉原文。
- 掌握度估计：画像是"学生自述"，没有答题正确率支撑，计划只能按薄弱章节加权。
- 考试公告抓取：流程表是手工维护的，长期应替换为带来源的官方公告 RAG。
- 教师端：没有"老师查看学生画像和错题"的接口，只有学生侧对话。
- Java 版同步：仍是电商场景，仅作对照实现。
